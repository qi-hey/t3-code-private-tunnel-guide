# OpenClash、FlClash 与直接路由

不要把“设备上运行了代理软件”理解为“所有流量都必须经过代理服务器”。

本方案只让特定 T3 连接进入 WireGuard 节点，WireGuard 的外层 UDP 直接访问自己的家庭入口。其他分流保持原状。

## 手机侧

生成的 FlClash 扩展：

- 保留原配置的代理组、DNS、TUN、现有节点和兜底规则。
- 添加专属 WireGuard 节点。
- 使用 `dialer-proxy: DIRECT`。
- 匹配“电脑地址 + T3 端口”，不把整个家庭网段或所有手机流量送入隧道。
- 将规则置于通用规则之前；重复执行不重复添加自己的节点。

改变 T3 端口后重新生成和应用扩展，旧的专属 T3 节点规则会被替换。DDNS 地址变更需要确认客户端重新解析；只检查域名字符串未变化是不够的。

生成的片段不包含完整订阅，不能直接替换订阅文件。FlClash 各版本的扩展入口和内核版本应现场核对。

## OpenWrt 侧

需要分别检查：

1. WireGuard 握手及封装后的 UDP 是否直接走正确的上游。
2. 从 `wg_t3` 解密进入的 T3 请求是否按普通路由到达电脑。
3. 电脑返回手机隧道地址的流量是否回到 WireGuard。
4. 是否有 OpenClash 的透明代理、`ip rule` 或 `fwmark` 改写了这三条路径。

可在现场私下检查 `ip rule show`、相关路由表和 nftables 规则。不要将整份带地址、设备标识的输出提交到公共仓库。

首先使用当前 OpenClash 版本支持的定向绕行能力。不要改动全局模式或关闭整个 OpenClash 来掩盖问题。

## 可选的 mark 规则

[nftables 示例](../templates/openclash-direct.nft.example)只展示按流量范围清除 mark 的一种办法，**不是必须执行的安装步骤**。

使用前必须确认：

- 干扰确实来自本隧道相关流量的 mark。
- 当前 firewall4 的 include 上下文及 nftables 版本接受该语法。
- `mangle + 5` 确实位于要绕过的处理之后；示例优先级不是跨版本保证。
- 后续链不会重新打标；多 WAN、QoS 或其他策略没有依赖这些流量的 mark。
- 没有更早发生的 TPROXY 接管等行为，仅清零 mark 不能撤销已经完成的所有处理。

示例限制为 WireGuard 出口 UDP 和特定 T3 双向流量。不要扩展为全局 `meta mark set 0`。

实际部署需要替换示例地址、端口和接口，执行 `fw4 check`，然后检查计数器与实际业务连接。卸载时仅移除本次创建且内容符合记录的专属 include 文件。
